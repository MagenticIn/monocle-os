The dynamic platform

The same process Spreo runs today — six stages, nine tabs, seven roles, the Needs List, the four gates — but held as rows in a database rather than written into the code. Change a stage, add a field, move a permission, define a second workflow for a different permutation: all of it becomes an administrator's edit, not a release.

Read this first. Decision D-016 put the workflow configuration engine and the admin studio out of Phase 1. Dan, on seeing it: "I see the word workflow, and that's why I didn't think that was part of this phase." Jonathan: "I love this engine… but I think we look at this as more phase two."

Nothing here contradicts that. The Phase 1 schema was deliberately built so this could be added without a rewrite — database/notes.md decision 2 says so in as many words: "The process is data. Stages, statuses, transitions, needs rules, the document catalogue, email templates, triggers, the role matrix and field visibility are all tables. Phase 1 seeds them and shows no screens; the Phase 2 admin studio is screens over these same tables." This document is what those tables have to grow into for that to be true, and what it costs.

Where the record settles something, it is reproduced exactly. Where the record is silent — above all the stage axis of the permission matrix, which Dan still owes — rows are marked assumed and are illustration, not instruction.

The configuration layer, in nine areas

Everything above the line is written by an administrator before a loan exists. Everything below it is written by the process as loans move. The line between them is the whole idea: the top half can change without a deploy, and the bottom half keeps its meaning because every row points at the version of the top half it was written under.

How a screen is built

What the server does between a user clicking a loan and the page rendering. Nine steps, no code branches — every decision is a lookup.

Permission explorer

This is the question the platform has to answer: for this field, in this group, at this stage, for this role, under this workflow — hidden, read, edit or required? Pick a combination. Every field in the catalogue resolves live, and why shows which grant row won and which it beat.

Permutations → the Needs List

The one genuinely automatic thing in Phase 1, generalised. Set the permutations on the left; the list on the right is generated by rules that are rows, and every item says which rule put it there. This same engine also picks which workflow the loan runs — shown at the top of the panel.

The stage machine, as rows

Six stages, twenty statuses, every legal move and what has to be true before it is allowed. None of this is code: a transition is a row, its gate is a condition tree, and its side effects are rows too. Adding a seventh stage is an insert.

What review found in this design

Every domain above was designed once and then attacked twice — once against the discovery record ("name a rule this cannot express") and once for buildability ("what does this cost on the hot path, and what breaks when an administrator misconfigures it"). These are the themes that survived, with the fix each one needs. They are listed because a design document that hides its own holes is worth less than one that does not.
